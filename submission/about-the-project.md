# About the project

Devpost story field. Markdown, no headings, freeflowing by design. Built from Sri's own hook draft, kept as close to his sentences as possible.

---

Every time I switched between building my startup and researching what I need to do to prepare for the vast world at Stanford, courses to research as an incoming freshman, using the same agentic models at my disposal for both, I was hit in the face with a sharp divergence in performance. The same model that built an entire secure backend meant to withstand ten thousand users while holding valuable information, and connected it to a frontend without trouble (dealing with the CORS errors alone took me hours just a few short years ago), was reduced to a useless machine awkwardly misclicking around Stanford Axess trying to retrieve any piece of information at all. It searched from stale sources and did not know what to do with broken links. It misclicked and accidentally closed out an enormous browsing session. It forgot everything about me in a matter of seconds. I saw that consumer AI was nowhere near frontier level, and the problem was context and browsing.

Which is why, when I heard that WebMCP, a concept I had heard of but never seen working, was actually moving forward, I was thrilled. This hackathon came at the right time, and with it the idea to finally streamline the process I had been struggling with all summer: pointing frontier intelligence at possibly the most important planning task of my adult life. I named it Acorn, an homage to the huge black squirrels, the infamous Stanford squirrels, that were darting around during my visit.

Acorn is a context layer more than it is a website. When we build with agents, we all keep markdown files in the repo so the model can carry goals, constraints, and decisions from one session to the next. Acorn takes that idea and turns it into a context window a person actually likes interacting with. You can talk to your agent and have it write things down, or scratch a half-formed idea into the pad yourself and have your agent make sense of it later. Either way you are both working on the same workspace: your goals, your protected hours, your notes on why CS 106B belongs in autumn, and a calendar that draws the week you would actually be signing up for.

The page registers 22 tools with the browser through `document.modelContext`. Every change, whether it comes from a human click or an agent call, runs through the same deterministic command layer with an expected version and an idempotency key, writes a receipt, and can be undone from the interface. The data is real: I imported Stanford's full public course feed, 15,618 courses across 256 departments, with 2,220 sections where each entry is a real enrollable week, a lecture paired with its discussion. Ask for a schedule and a deterministic solver enumerates the real section combinations, checks them against your protected windows, transition buffers, and club meetings, and returns ranked options the agent can apply with one undoable command. First responses from every read tool stay under 1,500 characters, because everything an agent reads comes out of its context window, and a tool that wastes that space is a bad tool.

The hardest question was how much to hardcode and how much to leave to the user's agent. A catalog nobody can trust is useless, and a catalog nobody can correct goes stale the day it is scraped. I ended up shipping verified reference data as the base and allowing edits on top of it. The student or the agent can amend any listing, every amendment carries a source, the interface shows the change against the original, and an unverified banner stays on the entry until someone re-checks it. The agent gets real autonomy, and nothing it does is silent.

To test all of this, I had Codex play the student. A Playwright bridge exposes the page's tools over HTTP, and across seventeen rounds a synthetic freshman lived in the workspace, planned quarters, joined clubs, and reported everything that felt wrong. Those rounds caught problems I would never have found clicking around myself. Saves took 32 seconds because undo snapshots had swollen the payload to 1.7 MB, so I cut it to 520 KB. A lost acknowledgment made the app claim a save that never happened, so writes now settle against a version probe and either adopt the server's truth or roll back visibly. A replayed command returned a conflict instead of its stored receipt, which broke safe retries, so replays became deterministic. The suite ended at 363 unit tests and 38 end-to-end browser tests, all green.

What I learned is that an agent is the strictest user I have ever designed for. It takes every description literally and fills every gap with something you did not intend, so the tools have to say exactly what they do, every mutation has to be safe to retry, and every change has to be inspectable after the fact. I also learned that the divergence I kept running into was never about intelligence. Once the browsing was replaced with typed tools and the context had a place to live, the same model that built my backend planned my quarter just as well.

Next, I want to ship the workspace barebones and give the agent more autonomy over it. The reference tools already let an agent research a university and build its catalog, programs, and clubs from official sources under the same provenance rules, so Acorn can extend beyond Stanford to any college, and past college to any long-running task where a person and their agent need one shared memory. The squirrels I named this after bury acorns all over campus and find them again months later, and that is what I want from planning with an agent: whatever the two of you put down, you come back and it is still there.
